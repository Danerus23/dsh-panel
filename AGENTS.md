# DSH Panel — правила работы в этом репозитории

Файл для человека и для ИИ-агента, который открыл репозиторий впервые. Читается за минуту, экономит
часы: здесь описано, чего нельзя делать, как проверять изменения, где что лежит и что уже сделано.
Репозиторий публичный: <https://github.com/Danerus23/dsh-panel>.

**Проект живёт на GitHub: то, чего нет в origin/main, для проекта не существует.** Законченная
работа — это закоммиченные и отправленные изменения; законченная версия продукта — это ещё и тег с
выпуском (см. «Выпуск»). Заканчиваешь правку — проверь git status и отправь.

## Что это

Панель управления локальным сервером **DeepSeek Harness** для Windows: C# / WinForms / .NET 8, один
исполняемый файл `DshTray.exe` в трее. Панель запускает и останавливает сервер `dsh web`, следит за
тарифом и балансом, делает резервные копии данных DSH и восстанавливает их, обновляет себя с GitHub
Releases. Интерфейс на трёх языках, установщик несёт внутри среду .NET Desktop Runtime 8, лицензия
MIT, автор — `Danerus23`. Устройство разобрано в `docs/DEVELOPMENT.md`.

## Красные линии (нарушать нельзя)

1. **Живой сервер и живая панель.** На машине владельца работает сервер DSH на порту **3080** и
   панель в трее. Их нельзя останавливать, а порт 3080 нельзя занимать своими проверками. Через
   этот сервер идёт сессия самого агента: остановишь — оборвётся ответ.
2. **Любая проверка — в изоляции.** Запускать панель из командной строки можно только с
   изолированными каталогами, иначе она прочитает и перезапишет настоящие данные:
   `DSH_PANEL_DATA`, `DSH_PANEL_STATE`, `DSH_PANEL_SSH_DIR`, `DSH_TRAY_BACKUP`, `DSH_HOME`,
   `DSH_PANEL_INSTANCE`, `DSH_PANEL_NO_MIGRATE=1`. Полная таблица подмен — в `docs/DEVELOPMENT.md`.
3. **`DshTray.exe` без аргументов — это GUI.** Запускать его без аргументов можно только человеку.
4. **Накат копии** (`--restore`) не запускать без `--from` с путём к копии, без изоляции и без
   свободного порта. Полную копию (`--backup --full`) на настоящем профиле не делать: она занимает
   сотни мегабайт и минуты.
5. **Личные данные не попадают в репозиторий.** Пути владельца, имена машин, логи, `settings.json`,
   `web-url.txt` (в нём токен входа), содержимое `~/.dsh` и снимки с балансом — только в
   `.gitignore`. Перед коммитом запускай `tools\check-personal.ps1`.
6. **Выпуски не переписываем задним числом.** Тег вида `v1.20.2` обязан совпадать с `<Version>` в
   `DshTray.csproj`: это проверяет CI и отказывается собирать выпуск. Если тег попал на неверный
   коммит, удали и тег, и выпуск, и поставь заново (см. «Выпуск»).
7. **Ничего не оставляем только на своей машине.** Репозиторий на GitHub — источник истины:
   изменения, которые не отправлены в origin/main, потеряются вместе с машиной. Закончил правку —
   закоммить и отправь. Закончил версию — поставь тег и выпусти релиз.
8. **Владельцу не мешать.** Перезапуск сервера и панели, установку «поверх» работающей панели и
   всё, что закрывает окна на его рабочем столе, делает только он сам, когда ему удобно.

## Как проверять изменения

**Быстрый цикл во время правки** (секунды, без установщика):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1            # сборка в .\app
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\acceptance.ps1 -Exe .\app\DshTray.exe
```

Работающую панель пересобрать нельзя: `.exe` и `.dll` заперты, пока панель в трее — сними её из
меню. Версия при быстрой сборке берётся из `<Version>`.

**Полный конвейер** (сборка, оба архива, установщик, все проверки, файлы выпуска, ничего не
публикует):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\make-release.ps1
```

Проверки и то, где они запускаются:

| Проверка | Что смотрит | В конвейере |
|---|---|---|
| `tools\acceptance.ps1` | 19 приёмочных проверок панели «как чужой» на изолированном профиле | да |
| `tools\check-restore.ps1` | копии и накат: что возвращается, что нет, предохранительная копия | да |
| `tools\check-autostart.ps1` | автозапуск: запись сверяется с этой копией и чинится; своя ветка реестра, настоящий `Run` проверяется отдельно | да |
| `tools\check-migrate.ps1` | перенос настроек из папки прежней генерации: файл панели НЕ перезаписывается (прежняя папка подменяется `DSH_PANEL_LEGACY_DATA`) | да |
| `tools\check-notes.ps1` | собранное тело выпуска: три языковых блока из трёх историй, версия, порядок меток, отсутствие HTML, побайтная повторяемость | да |
| `--node-check` (по собранной панели) | адреса и имена файлов для установки Node отвечают — иначе установка Node у людей падает с 404 (`tools\make-release.ps1:145-152`) | да |
| `tools\check-update.ps1` | путь обновления на локальной заглушке GitHub: суммы, распаковка, сценарий | да |
| `tools\check-update-apply.ps1` | **сама замена файлов** в папке с пробелом (см. урок ниже) | да |
| `tools\check-lang.mjs` | словари: три языка, одинаковый набор ключей и подстановок | да |
| `tools\check-encoding.ps1` | `.ps1` и `.iss` — UTF-8 **с BOM** и переводы строк CRLF | да |
| `tools\check-personal.ps1` | личные данные сборщика в текстовых файлах, которые уедут в репозиторий: отслеживаемые И новые, ещё не добавленные в индекс (`git ls-files --cached --others --exclude-standard`). Внутрь PNG и ZIP не смотрит — снимки вне её охвата, это печатается в выводе | да |
| `tools\pack-panel.ps1` | раздатка: собирает архив и проверяет, что в него не уехали отчёты, настройки, `web-url.txt` (в нём токен входа) и логи | да |
| `tools\check-versions.ps1` | версия в проекте, штампе, скрипте установщика, самом установщике и архивах | да |
| `tools\check-installed.ps1` | установленная панель: удаление, «Программы и компоненты», вёрстка | **нет** — ставит панель, гоняется руками |
| `tools\check-onboarding.ps1` | мастер первой настройки открывается одним окном | **нет** — нужен рабочий стол |
| `tools\verify-release.ps1` | **уже опубликованный** выпуск: суммы, версии установщика и архива | **нет** — ходит в GitHub |

Правило: **ноль — успех, ненулевой код — провал**, у каждой проверки в конце печатается таблица.
Исключение — `check-onboarding.ps1`: код 2 означает «пропущено, рядом работает другая панель» (её
процесс не наш, второй экземпляр выходит сразу), а не «нет рабочего стола»: без рабочего стола мастер
не открывается вовсе, и это код 1 — такая же ошибка, как два окна мастера.
«Конвейер зелёный» не значит «проверено всё»: строки, где в таблице «нет», в него не входят.

Проверка в чистой Windows живёт **вне репозитория**, на рабочей машине владельца: стенд
`..\dsh-deploy\test-stand` (сборка раздатки `prepare-panel-payload.ps1`, подключение ISO к Hyper-V
`use-payload-iso.ps1` и `repair-vm-iso.ps1`), а сборщик отчёта `СОБРАТЬ-ОТЧЁТ.cmd` лежит внутри
`test-stand\payload-panel\`. С нуля этот стенд не воспроизводится: он требует Hyper-V, ISO Windows и
участия человека.

## Грабли, на которые уже наступали

- **Пробел и хвостовой `\` в пути установки ломают обновление.** Панель ставится в
  `%LOCALAPPDATA%\Programs\DSH Panel`, и этот путь однажды ушёл в сценарий замены как
  `"…\DSH Panel\"`: командная строка съела закрывающую кавычку, robocopy получил ключи `/E /NFL`
  как часть пути и отказался копировать (ошибка 123). Сценарий откатился, панель поднялась прежней
  версии. Теперь хвостовые разделители срезает `UpdateService.SafePath`, а весь путь целиком
  проверяет `tools\check-update-apply.ps1`. **Правило: проверки путей делай на пути с пробелом.**
- **После `git init` версия exe становится `1.20.2+<хеш коммита>`.** .NET вписывает хеш в
  `ProductVersion`, поэтому сравнения версий (инструменты и сам апдейтер) обязаны брать числовую
  часть: `(... -split '\+')[0]`. Панель это делает (`UpdateService.Clean`) — инструменты тоже.
- **`.ps1` и `.iss` требуют BOM.** Инструменты правки (`edit`, `write`) BOM снимают, и PowerShell 5.1
  после этого ломает кириллицу. После правки прогоняй `tools\check-encoding.ps1 -Fix`.
- **`.json` — наоборот, без BOM.** Словари и `settings.json` читаются без него; BOM ломает разбор.
- **Не перезаписывай ISO, на который смотрит виртуальная машина.** Hyper-V выдаёт права на файл в
  момент подключения привода; после подмены файла ВМ не запускается с «Отказано в доступе». Раздатка
  всегда собирается под новым именем.
- **Снимки для README снимаются на нейтральном профиле.** Рецепт: `DSH_TRAY_NODE` и `DSH_TRAY_BIN`
  ведут в `C:\Users\Public\DshPanelDemo\node\...`, `DSH_PANEL_SSH_DIR` — в ту же демонстрационную
  папку, `DSH_TRAY_BACKUP` — в её `backups` с **обезличенной** демо-копией, `language` в настройках —
  `auto`, порт — заведомо свободный (например 3095), `DSH_HOME` — свой пустой, а `DSH_PANEL_RUN_KEY` —
  в свою временную ветку реестра (иначе галочка «Запускать при входе в Windows» рисуется из
  **настоящего** `HKCU\...\Run`: её состояние читает `Autostart.IsEnabled`, и кадр покажет состояние
  машины снимающего, а не демо-профиля). Тогда в кадр не
  попадут ни имя владельца, ни имя машины, ни баланс, ни чужой порт. Снимки рисует сама панель:
  `DshTray.exe --shot <папка>\panel.png` (рядом отчёт из `--out`). Помни: `DrawToBitmap` не рисует
  текст выпадающих списков, поэтому мастер на снимке выглядит с пустым полем языка — это артефакт
  съёмки, а не ошибка; поэтому шаг мастера в таблицу README не выносим. Демо-копию для кадра
  наката приходится обезличивать **вручную**: панель всегда пишет в опись `Environment.MachineName`
  и имя пользователя, а ключа «обезличить» в командной строке нет — прежняя демо-копия один раз
  вынесла в кадр настоящее имя машины и имя владельца, и нашёл это OCR снимков, а не глаза. Витрина
  README — коллаж `docs\demo.png`; его собирает `tools\make-demo-collage.ps1` из четырёх кадров
  `docs\screenshots\en`, поэтому **после пересъёмки снимков коллаж надо пересобрать** — иначе в
  README останутся окна прежней версии.
- **Дубль раздела версии в истории выбирается молча — первым.** `Read-Section` в
  `release-notes.ps1` берёт первое совпадение `## <версия>`, поэтому второй раздел с той же версией
  (так бывает при переносе перевода) в тело выпуска не попадёт, и заметки разойдутся с файлом.
  Ловит `tools\check-notes.ps1`: в русской истории раздел обязан быть ровно один, в переводах —
  ноль или один.
- **Установка поверх работающей панели** (обновлено в 1.21.0). Раньше в `[Setup]` стоял
  `AppMutex=Local\DshTray.SingleInstance`, и Inno показывал **неподавляемое** окно «панель уже
  работает» ещё до `[Code]` — то есть раньше нашего `taskkill`. Для обычной установки это было
  терпимо, а для `winget upgrade` смертельно: панель в трее почти всегда работает, и автоматический
  прогон вставал на окне, которого никто не закроет (при «Cancel» — код 5, «отменено
  пользователем»). Теперь мьютекс убран, а панель закрывает наш собственный `taskkill` — он
  срабатывает в начале копирования файлов (`CurStepChanged`, шаг `ssInstall`). `CloseApplications=yes`
  добавляет к этому родной механизм Inno: работающая панель **видна** ему через Restart Manager
  (проверено пробой), и в обычной установке Inno перечисляет её среди закрываемых приложений.
  `[UninstallRun]` с `taskkill` остался. **Честно: вживую это не проверялось** — вывод из справки
  Inno и кода, поэтому установку поверх работающей панели стоит один раз проверить в виртуальной
  машине.
- **В тихой установке не должно быть ни одного окна.** Дважды на этом спотыкались: приглашение Inno
  «This will install…» не отключается ключами `/SILENT` и `/VERYSILENT` (снимается
  `DisableStartupPrompt=yes` и ключом `/SP-`), а `MsgBox` из `[Code]` вообще не глушится
  `/SUPPRESSMSGBOXES` (справка Inno перечисляет такие окна прямо). Поэтому в установщике все
  сообщения идут через процедуру `SayOrLog`: человеку за экраном — окно, в неинтерактивном прогоне —
  строка в журнале установки. Появляется новое сообщение — только через неё.
- **Двойной BOM — тоже поломка, и она была невидимой.** Один файл однажды записался как
  `EF BB BF EF BB BF`: лишний `U+FEFF` перед `#` делал первую строку кодом, `param(` перестал быть
  ключевым словом, и скрипт не запускался ни в PowerShell 5.1, ни в 7 — а проверка кодировки смотрела
  только первые три байта и молчала. Теперь `tools\check-encoding.ps1` считает **все** ведущие BOM и
  ловит `U+FEFF` внутри текста.
- **После мастера панель перезапускает себя** (`TrayHost.RestartSelf`): панель, которая ставила Node
  и движок, несёт окружение до установки, и сервер с первого раза не поднимается.
- **Запись автозапуска хранит абсолютный путь — её обязательно сверять.** `HKCU\...\Run`
  (`DSHPanel`, прежнее имя `DeepSeekHarness`) указывает на конкретный exe, поэтому на машине может
  стоять несколько копий, а папку можно перенести. Панель делает это при каждом старте
  (`Autostart.Repair`): переносит прежнее имя на себя (запись под прежним именем переводится
  всегда — иначе старая копия осталась бы в автозапуске навсегда), переводит запись с мёртвого
  файла и с более старой копии, а живую соседнюю копию той же или более новой версии не трогает и
  говорит о ней пунктом меню трея и подсказкой галочки в окне панели (шарик про такую запись не
  показывается — исправлять там нечего). Галочка «запускать при входе» отвечает на вопрос «запись
  есть?» (`Autostart.IsEnabled`), а КУДА она ведёт — это `Autostart.Inspect()`: при записи на
  чужую копию пункт меню и подсказка говорят об этом прямо. Установщик (`installer\dsh-panel.iss`)
  приводит существующую запись к `{app}` и убирает прежнее имя при установке и при удалении:
  `UsePreviousTasks=no` (прежний выбор задач не восстанавливается — иначе тихая установка вернула бы
  уже снятый человеком автозапуск), запись `DSHPanel` пишется ДВУМЯ строками `[Registry]` (по задаче
  `autostart` и по `Check: AutostartWasSetCheck`), имя `DeepSeekHarness` удаляется и при установке, и
  при удалении, а ярлык прежней генерации `DeepSeek Harness.lnk` убирается только там, где ведёт на
  `DshTray.exe` (на рабочем столе, в «Программах» и в группе установщика). Проверяет
  `tools\check-autostart.ps1`, уводя реестр в свою ветку через `DSH_PANEL_RUN_KEY`. **Честно: эта
  часть установщика не покрыта ни одной автоматической проверкой** — `check-autostart.ps1` гоняет
  только `--autostart-fix` самой панели, поэтому правки `[Registry]` установщика и уборку ярлыка
  проверяют компиляцией установщика и руками в виртуальной машине. **Правило:
  сохранённую ссылку на себя сверяй при старте; молча отбирать автозапуск у соседней копии
  нельзя; проверка с подменёнными каталогами настоящий `Run` не трогает вообще** (это уже
  случалось: проверка замены файлов перенаправила запись владельца на свою временную копию).
  **И уведомлять она тоже не должна — ни окон, ни шариков.** Это отдельная грабля, найденная
  21.09.2026: предохранитель запрещал прогону проверки *писать* в реестр, но `CheckAutostart`
  всё равно показывал шарик, если запись вела на живую соседнюю копию. Наши же проверки запускают
  собранную панель с тем же номером версии, что стоит у владельца, поэтому он получал на своём
  рабочем столе предупреждение о **своём** автозапуске, которое к проверке отношения не имело.
  Теперь решение о показе вынесено в `Autostart.ShouldNotify(state, isolatedRun)`: в изолированном
  прогоне — никогда, про живую соседнюю копию — нет (это видно в пункте меню трея и в подсказке
  галочки в окне панели; подсказка значка об автозапуске молчит), а шарик остаётся только для
  неисправимого: запись ведёт на отсутствующий файл или реестр не читается.
  **Признак изоляции один на всю панель — `Autostart.IsIsolatedRun`** (подменены каталоги панели
  **или** ветка реестра), и через единую дверь `TrayHost.NotifyBalloon` он закрывает **все**
  автоматические сообщения, а не только автозапуск: шарики о новой версии, об итоге обновления,
  об окнах пика, о балансе, о неудачной копии и фоновые ошибки (подавленное сообщение остаётся
  в журнале).
  **Окна — по тому же правилу, и это вторая половина той же грабли** (найдена 22.09.2026):
  изолированный прогон показывал человеку **окно мастера первой настройки** — `tools\check-update-apply.ps1`
  поднимает панель без ключей в свежем профиле, а таймер старта открывал модальный мастер поверх
  его работы (в `%TEMP%` набралось 16 таких песочниц). Теперь решения вынесены в чистые предикаты,
  которые перебирает самопроверка: `TrayHost.ShouldAutoShowOnboarding(onboarded, requested, isolated)`
  — мастер показывается, только если его просили ключом `--onboard` (на этом стоит
  `tools\check-onboarding.ps1`) или если профиль настоящий и мастер в нём не пройден;
  `TrayHost.ShouldAutoOpenBrowser(isolated)` — браузер при старте в изоляции не открывается;
  `TrayHost.ShouldShowWindowOnStart(onboarded, isolated)` — окно панели тоже;
  `TrayHost.ShouldAutoStartServer(isolated)` — и **сам сервер** при старте не поднимается;
  `TrayHost.ShouldShowPanelOnSignal(isolated)` — окно не показывается по запросу «покажи окно»
  от второго запуска ярлыка. Подавленное решение пишется строкой в журнал у **каждого** гейта,
  поэтому «панель молчала» видно без окна (прежде гейт окна писал строку только у пройденного
  профиля, а гейт мастера — только у непройденного).
  **Третья половина той же грабли** (найдена независимой проверкой 22.09.2026): изолированный
  прогон `check-update-apply` читал настоящий `~/.dsh` владельца (в песочный профиль не подменялся
  `DSH_HOME`) и показывал в журнале **его баланс**, а свежий `settings.json` нёс `serverPort = 3080`
  — то есть автозапуск сервера целился в **живой** порт владельца: останови он свой сервер, наша
  проверка подняла бы `dsh web` на 3080 в его же `~/.dsh`, а `Stop-Process -Force` оставил бы порт
  осиротевшему `node`. Поэтому: (1) признак изоляции считается по **всему** перечню подмен данных
  (`Autostart.IsolationOverrides`: `DSH_PANEL_DATA`, `DSH_PANEL_STATE`, `DSH_PANEL_SSH_DIR`,
  `DSH_TRAY_BACKUP`, `DSH_HOME`, `DSH_PANEL_LEGACY_DATA`, `DSH_PANEL_INSTANCE`, `DSH_PANEL_RUN_KEY`,
  `DSH_PANEL_NO_MIGRATE`), а не по четырём переменным, и самопроверка перебирает **каждую** из них;
  (2) автоматический запуск сервера заглушён, а песочный профиль проверки, которая поднимает панель
  как GUI, обязан нести свой свободный порт (у `check-update-apply` он теперь есть, и проверка это
  утверждает). Подмены «на один прогон», которыми пользуется человек (`DSH_PANEL_LANG`,
  `DSH_TRAY_NODE`, `DSH_TRAY_BIN`, `DSH_TRAY_PRICING`, `DSH_PANEL_API`, `DSH_PANEL_REPO`),
  изоляцией **не считаются** — иначе панель молчала бы у человека с переносимым Node.
  **Граница «человек видит против проверка считает»:** глушится всё, что окно или шарик на рабочем
  столе владельца, и всё, что заняло бы порт владельца; **не** глушится то, что проверки читают,
  — в первую очередь **явный** запуск сервера ключом `--server-start` (`tools\acceptance.ps1`
  поднимает его на своём песочном порту и считает ссылку входа) и значок трея
  (`--selftest`/`--layout-check` поднимают настоящий `NotifyIcon`, и структурные кейсы работают
  именно с ним).
  Кейсы самопроверки — «Автозапуск ок», «Обновления ок», «Уведомления ок», «Шарики ок»,
  «Автоматика старта ок», «Мастер ок», «Видимое при старте ок», «Изоляция ок» и «Гейты ок».
  Последние два важны по-своему: «Изоляция ок» берёт перечень переменных **у самого признака**,
  выставляет по одной каждую, проверяет `Autostart.IsIsolatedRun` и `Autostart.IsCheckRun`, а
  решение двери проверяет **значением** (`TrayHost.DoorDecision` молчит для каждого вида) — одних
  ссылок на предикат мало: дверь `ShouldNotify(kind, IsIsolatedRun && NeverTrue())` ссылки имеет,
  а показывает всё; а «Гейты ок» читает IL и требует, чтобы дверь, мастер, окно, запрос «покажи
  окно» и серверный старт спрашивали свой предикат и изоляцию.
  **Честно про структурный кейс «Шарики ок»:** дверью считается любой метод, который зовёт шарик
  **и** спрашивает решение двери, а список интерактивных сайтов — явный allow-list, который можно
  сокращать (провести шарик «свёрнуто в трей» через дверь — улучшение, и кейс молчит). Ловится
  прямой вызов (`call`/`callvirt`) и ссылка на метод для делегата (`ldftn`/`ldvirtftn`) в любой
  точке сборки, но **не** ловится умышленное отражение по имени
  (`GetMethod("ShowBalloonTip").Invoke(...)`) — там имя метода обычная строка. Обещать «ни один
  шарик не проскочит» нельзя; гарантия — «ни прямой вызов, ни делегат».
- **Параметр `Check` в Inno принимает ФУНКЦИЮ, а не переменную.** `Check: AutostartWasSet` (булева
  переменная) валит компиляцию сообщением «Required function or procedure 'AutostartWasSet' not
  found» — нужна функция-обёртка. Запись автозапуска пишется ДВУМЯ строками `[Registry]`: одна по
  родному механизму `Tasks: autostart` (состояние галочки читает сам Inno), вторая по
  `Check: AutostartWasSetCheck` (запись уже была до установки). Дубль для `[Registry]` — не ошибка
  и не предупреждение, данные идентичны. Компиляция проверяется так:
  `installer\build-installer.ps1 -SkipBuild -SkipRuntime -AppDir <папка сборки>`.
- **Node нужен не только переводам.** `check-lang.mjs` и обе проверки обновления поднимают заглушку
  на Node, поэтому без него конвейер не пройдёт.

## Как работает обновление панели

1. Панель спрашивает `releases/latest` репозитория (`UpdateService.Repository`; подменить адрес для
   проверки можно через `DSH_PANEL_API`). Проверка идёт **при каждом запуске** панели, но шарик о
   новой версии показывается **один раз на версию** (`UpdateService.ShouldAnnounce`): иначе при
   каждом старте человек получал бы одно и то же сообщение. Ничего сама не скачивает.
2. `--update-check` только сообщает, что есть новее; `--update-prepare [--force]` скачивает архив,
   сверяет `SHA256SUMS.txt`, распаковывает в `<состояние>\update\<версия>`, проверяет версию внутри
   и **печатает готовую команду замены** — её видно и можно запустить руками.
3. Команда запускает `update.cmd`: он ждёт выхода панели по её PID, дожидается освобождения мьютекса
   и копирует файлы robocopy. При ошибке откатывается на копию прежней версии. Панель поднимается
   только там, где файлы на месте — после удачной замены или после удачного отката; в ветках «панель
   не вышла», «мьютекс занят», «проверить мьютекс не удалось», «откат не удался» и «страховочной
   копии нет» не запускается ничего, а следы (копия прежней версии, скачанная сборка, журнал
   `update.log`) остаются для ручной починки.
4. Весь этот путь целиком проверяет `tools\check-update-apply.ps1`.

## Выпуск

Источник истины по версии — `<Version>` в `DshTray.csproj`. Остальные места (штамп `build.txt`,
`appversion.iss`, номер внутри установщика, версия внутри архивов) **создаются сборкой**, их
сверяет `tools\check-versions.ps1`. Вручную правят четыре места: `<Version>` в проекте и раздел
новой версии в каждой из трёх историй (`CHANGELOG.md`, `CHANGELOG.en.md`, `CHANGELOG.zh.md`).

```powershell
# 1. поднять версию и описать изменения:
#    DshTray.csproj: <Version>1.21.0</Version>;
#    CHANGELOG.md, CHANGELOG.en.md, CHANGELOG.zh.md: раздел «## 1.21.0 — <дата>»
# 2. прогнать конвейер и убедиться, что всё зелёное
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\make-release.ps1
# 3. закоммитить, поставить тег и отправить его — дальше работает CI
#    ВАЖНО: без git push ничего из этого не существует ни для кого, кроме этой машины.
git add -A; git commit -m "..."; git push origin main
git tag -a v1.21.0 -m "DSH Panel 1.21.0"; git push origin v1.21.0
# 4. ПОСЛЕ публикации — пересобрать манифест winget под выпущенную версию (см. «Пакет для winget»)
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\winget-manifest.ps1 -ReleaseTag v1.21.0 -Validate
```

CI (`.github/workflows/build.yml`) ставит .NET 8, проверяет словари, совпадение тега с версией,
кодировку и личные данные, собирает панель и оба архива, на теге добавляет установщик, сверяет
версии, пишет `SHA256SUMS.txt`, собирает тело выпуска из трёх историй и проверяет его
(`tools\check-notes.ps1`), затем job `release` создаёт выпуск с
четырьмя файлами: `dsh-panel-setup.exe`, `DshPanel.zip`, `DshPanel-selfcontained.zip`,
`SHA256SUMS.txt`. Экшены закреплены по SHA коммита; проверить актуальность:
`gh api repos/<owner>/<repo>/commits/<tag> --jq .sha`.

Проверить уже опубликованный выпуск (скачает ассеты, сверит суммы и версии):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\verify-release.ps1 -Tag v1.20.3
```

## Пакет для winget

В `winget/` лежат три манифеста схемы 1.12.0 (`Danerus23.DSHPanel.yaml`,
`Danerus23.DSHPanel.installer.yaml`, `Danerus23.DSHPanel.locale.en-US.yaml`): установщик Inno,
область пользователя, без зависимостей, с `RequireExplicitUpgrade: true` — иначе
`winget upgrade --all` дёргал бы панель, у которой своих обновлений больше, чем этого манифеста.
Заполняет и проверяет их `tools\winget-manifest.ps1`: версия берётся из `<Version>`, а SHA-256 —
**из выпуска** (`-ReleaseTag v<версия>`), потому что установщик собирает CI и байты его файла
отличаются от локальной сборки в `dist\`. Локальную сумму скрипт писать отказывается (только с
явным `-AllowLocalSum` — для отладки), а несовпадение тега с версией проекта считает ошибкой.

Манифест в репозитории **отстаёт от версии проекта на один выпуск, и это нормально**: он описывает
то, что уже опубликовано. Порядок такой: выпустить версию, затем пересобрать манифест
(`-ReleaseTag v<версия> -Validate`) и отправить его в `microsoft/winget-pkgs` отдельным pull
request — первый PR требует подписать CLA в браузере. Подпись кода для winget не нужна.

## Донаты

Донаты идут через lava.top. Ссылка заполнена в `AppLinks.DonateUrl`
(`https://app.lava.top/3686297587`), поэтому строка «Поддержать проект» есть в «О панели», и та же
ссылка стоит в разделе о поддержке во всех трёх README. Если ссылка пуста, строка в панели просто не
показывается — это сделано намеренно, кнопки «в никуда» в продукте нет. Меняешь ссылку — поправь
`AppLinks.cs`, три README и `.github/FUNDING.yml` сразу.

`.github/FUNDING.yml` даёт кнопку «Sponsor» на странице репозитория. GitHub сам денег не переводит —
он только показывает ссылку, а сбор идёт на стороне сервиса. Внутренняя программа **GitHub Sponsors**
нам недоступна: её выплаты не подключаются для получателей из России, поэтому кнопка ведёт на
lava.top, который уже работает. Patreon можно добавить туда же (`patreon:` или вторым адресом в
`custom`) — но только если деньги с него действительно доходят: сложность не в GitHub, а в выплатах
в Россию.
